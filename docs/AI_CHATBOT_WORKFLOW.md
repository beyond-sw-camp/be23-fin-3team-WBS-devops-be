# WMS AI Chatbot Workflow Guide

이 문서는 WMS AI 챗봇 작업을 할 때 반드시 먼저 읽어야 하는 설계 기준이다.
사용자가 매번 같은 의도를 다시 설명하지 않아도, 아래 기준을 기본 전제로 삼고 구현한다.

## 목표

챗봇은 단순 템플릿 응답기가 아니라 WMS 업무 흐름을 이해하고, 현재 업무 데이터와 문서 지식을 적절히 연결해 사용자에게 다음 행동을 안내하는 업무 보조자다.

답변은 빠르기만 하면 안 된다. 사용자가 "정상적으로 이해하고 답했다"고 느낄 수 있어야 한다.

## 핵심 원칙

- 단순 땜빵 금지. 조건문으로 특정 문장만 맞추는 방식보다 라우팅, 프롬프트, 데이터 근거, 답변 생성 흐름을 함께 정리한다.
- 사용자의 질문 의도를 먼저 존중한다. "어떻게 해?", "왜 안 돼?"처럼 방법이나 실패 원인을 묻는 질문은 현재 데이터 조회가 아니라 운영 지식 답변으로 본다.
- 템플릿은 장애 fallback 또는 아주 단순한 빈 결과 안내에만 사용한다. 정상 답변은 가능하면 LLM이 조회 결과와 대화 맥락을 보고 생성한다.
- 조회 결과가 있으면 내부 컬럼명, UUID, SQL을 노출하지 않고 업무 용어로 바꿔 말한다.
- 조회 결과가 없으면 "죄송합니다. 처리할 수 없습니다."처럼 실패처럼 보이게 말하지 않는다. 사용자 질문 기준으로 자연스럽게 없는 상태를 설명한다.
- 답변은 사용자가 바로 다음 화면에서 무엇을 해야 하는지 알 수 있게 끝나야 한다.

## 라우팅 기준

챗봇 라우팅은 크게 네 가지다. 민감정보 차단은 가장 앞단에서 먼저 수행한다.

- `BLOCKED`: 개인정보/민감정보 조회 또는 노출을 요구하는 질문. 예: 직원 전화번호, 이메일, 로그인 아이디, 비밀번호, 토큰, 주민등록번호.
- `WORK_QUERY`: 현재 DB 상태를 확인해야 하는 질문. 예: 재고 위치, 출고 가능 수량, 오늘/내일 처리할 작업, 내 피킹 작업, 미처리 지시서.
- `RAG`: 매뉴얼/정책/절차/상태 의미/실패 원인/화면 경로를 설명해야 하는 질문. 예: 상태값 의미, 화면 사용법, 예외 처리 기준, 작업 실패 원인, 불량 사진 확인 위치.
- `GENERAL`: 인사, 감사, 챗봇 소개, 도움말처럼 데이터나 문서 근거가 필요 없는 대화.

`BLOCKED`는 `WORK_QUERY`, `RAG`, `GENERAL`보다 우선한다. 차단된 질문은 API 호출, RAG 검색, 답변 생성 LLM으로 넘기지 않는다.
차단 응답은 고정 문구를 사용한다.

```text
해당 정보는 개인 정보에 해당되어 답변이 불가합니다.
```

특정 상품명이 포함되어도 방법/절차/실패 원인을 묻는 질문은 `RAG`로 본다. 예: "유선 마우스 출고 어떻게 해?", "출고 지시서 생성이 왜 실패해?".
사진, 증빙, 첨부 파일, 화면 위치를 묻는 질문도 `RAG`로 본다. 예: "불량 사진 어디서봐?", "증빙 파일 어느 메뉴에서 봐?".
현재 재고 위치, 가용 수량, 작업 목록처럼 DB의 현재 상태를 직접 묻는 질문만 `WORK_QUERY`로 본다.

단, "출고 절차가 뭐야?", "피킹 리스트가 뭐야?"처럼 상품/현재 대상이 없는 일반 절차 질문은 `RAG`로 볼 수 있다.

## WORK_QUERY 흐름

정상 흐름은 아래 순서를 따른다.

1. LLM 또는 충분히 일반화된 라우터가 질문 의도를 판별한다.
2. 필요한 슬롯을 추출한다. 예: 상품명, 창고명, 날짜, 상태.
3. 질문 의도에 맞는 업무 서비스 API를 호출한다.
   - stock-service: 재고, 입고/출고, 피킹, 부족 재고, 처리할 작업
   - master-service: 상품, 창고, 구역/랙/로케이션, 공급사, 매장/출고처
   - account-service: 사용자 역할, 권한, 고객사 같은 관리 정보
4. 조회 결과를 사용자 질문, 최근 대화 맥락, 의도와 함께 LLM 프롬프트에 넣는다.
5. LLM이 조회 결과만 근거로 자연어 답변을 작성한다.
6. LLM 실패 또는 빈 응답일 때만 fallback 문장을 사용한다.

정상 WORK_QUERY 답변에서 `llmMs=0`이고 `fallback=true`로 끝나면 의심해야 한다. 의도적으로 LLM을 생략한 템플릿 우회가 아닌지 확인한다.

## 민감정보 차단 흐름

SLLM은 사용하지 않는다. OpenAI 기반의 분류 전용 프롬프트로 개인정보 여부만 먼저 판단한다.

정상 흐름은 아래 순서를 따른다.

1. 사용자 질문을 민감정보 분류 프롬프트에 넣는다.
2. 분류 결과가 `BLOCK`이면 즉시 고정 차단 문구를 반환한다.
3. `BLOCK`이면 업무 API 호출, RAG 검색, 일반 답변 생성을 하지 않는다.
4. 분류 결과가 `ALLOW`이면 기존 라우팅(`WORK_QUERY`, `RAG`, `GENERAL`)으로 진행한다.
5. 분류 LLM 호출이 실패했고 질문에 전화번호/이메일/비밀번호/토큰 등 명확한 민감정보 키워드가 있으면 보수적으로 차단한다.

차단 대상:

- 주민등록번호, 외국인등록번호, 여권번호, 운전면허번호
- 비밀번호, 토큰, API Key, Secret, 인증번호, OTP
- 개인 전화번호, 휴대폰 번호, 연락처, 개인 이메일, 집주소, 생년월일
- 계좌번호, 카드번호, 급여, 개인 신상정보
- 특정 직원/사용자/관리자의 로그인 아이디 등 개인 계정 식별자

허용 대상:

- 재고 위치, 입고/출고 현황, 작업 목록, 지시서 상태
- 상품, 창고, 구역, 랙, 로케이션, 공급사, 매장 같은 업무 기준 정보
- 사용자 역할명/권한 정책처럼 개인 연락처나 인증정보를 노출하지 않는 관리 정보
- 개인정보 처리 방법이나 보안 정책에 대한 일반 설명

## RAG 문서 반영 기준

운영 배포 후 개발자가 Postman으로 문서를 수동 ingest하지 않는다.
`ai-service`는 기동 시 `classpath:/knowledge/*.txt` 문서를 자동으로 읽고 pgvector에 upsert한다.

- 기본 설정: `wms.rag.auto-ingest.enabled=true`
- 기본 위치: `classpath:/knowledge/*.txt`
- 각 파일명에서 확장자를 뺀 값을 `metadata.source`와 `metadata.category`로 사용한다.
- 같은 `source`가 이미 있으면 기존 청크를 삭제한 뒤 새 청크를 저장한다.
- 특정 환경에서 자동 반영을 끄려면 `RAG_AUTO_INGEST_ENABLED=false`로 설정한다.

따라서 `wms-ui-guide.txt` 같은 지식 문서를 수정하고 ai-service를 배포하면, 서비스 시작 시 새 내용이 vector_store에 반영된다.

## 출고 방법 질문 답변 기준

질문 예시: "유선 마우스 출고 어떻게 해?", "무선 마우스 출고 원해".

좋은 답변은 운영 절차와 화면 기준을 말한다. 이 질문에서는 재고 조회 API를 함께 호출하지 않는다.

예시:

```text
출고 지시서는 출고 관리 > 출고 지시서에서 생성한 뒤 승인하고, 승인 완료 상태에서 피킹 리스트를 생성합니다. 생성이 실패하면 가용 재고, 출고 창고, 상품 활성 여부, 매장/거래처 정보를 먼저 확인해 주세요.
```

답변에 포함해야 할 정보:

- 화면 경로
- 다음 업무 단계: 출고 지시서 생성, 승인, 피킹 리스트 생성
- 실패 시 확인할 조건: 가용 재고, 창고/상품/매장 정보, 상태값

재고 위치나 수량이 필요한 경우에는 사용자가 별도 질문으로 "유선 마우스 재고 어디 있어?", "출고 가능 수량 알려줘"처럼 물어야 한다.

예시:

```text
출고 지시서 생성이 실패했다면 먼저 재고 조회 화면에서 해당 상품의 가용 수량과 예약 수량을 확인하고, 출고 창고와 매장 정보가 올바른지 확인해 주세요.
```

## 날짜/작업 질문 답변 기준

질문 예시: "내일은?", "4월 30일에 뭐 있어?", "오늘 뭐 해야 돼?"

날짜 표현은 사용자가 말한 표현을 최대한 보존한다.

- 오늘: "오늘은 ..."
- 내일: "내일은 ..."
- 어제: "어제는 ..."
- 4월 30일: "4월 30일에는 ..."

빈 결과는 실패가 아니라 부재로 답한다.

예시:

```text
내일은 처리할 작업이 존재하지 않습니다.
```

할 일이 있는 경우에는 업무 유형, 문서번호, 창고, 담당자를 자연스럽게 말한다.
사용자가 "뭐 해야 돼?"처럼 행동을 물으면 마지막 문장은 가능하면 "~해야 합니다."로 끝낸다.

## 재고 위치 질문 답변 기준

질문 예시: "무선 마우스 어디 있어?", "케이블 어디야?"

좋은 답변은 위치만 말하지 않고 재고 판단에 필요한 수량도 함께 말한다.

예시:

```text
무선 마우스는 서울중앙창고의 LC-RK-ZN-SEL-ELEC-002-TECH-003-02 위치에 있으며, 현재 가용 수량은 320개입니다.
```

여러 위치가 있으면 우선 상위 몇 개를 요약하고, 필요하면 추가 조회를 유도한다.

## 답변 품질 기준

- 사용자가 화면에서 확인 가능한 업무 용어를 쓴다. 예: 출고 지시서, 승인, 피킹 리스트, 적치 지시서, 재고 현황.
- 내부 구현 용어를 노출하지 않는다. 예: intent, slots, fallback, rows, SQL, UUID.
- "처리할 수 없습니다"는 실제 오류가 아니라면 쓰지 않는다.
- 한 답변에 너무 많은 절차를 길게 나열하지 않는다. 보통 1~2문장으로 충분하다.
- 현재 화면과 다음 행동이 연결되면 좋다. 예: "재고 현황에서 확인", "출고 지시서를 생성", "피킹 리스트를 생성".

## 로그 해석 기준

정상적인 LLM 기반 WORK_QUERY는 보통 아래 로그가 함께 나타난다.

- `AI_CHAT_ROUTE`: WORK_QUERY로 라우팅
- 민감정보 질문이면 `AI_CHAT_ROUTE`: BLOCKED로 라우팅
- `AI_WORK_QUERY_ROUTE`: intent와 slots 판별
- `AI_WORK_QUERY_API`: stock/master/account-service 조회 결과
- 절차/실패 원인이 필요한 질문이면 `AI_RAG_CONTEXT`
- `AI_WORK_QUERY_LLM_START`
- `AI_WORK_QUERY_LLM_END`
- `AI_WORK_QUERY_END`: `llmMs`가 0보다 크고, 정상 생성이면 `fallback=false`

`fallback=true`는 실패 fallback과 템플릿 fallback을 혼동하게 만들 수 있다. 로그 개선 시에는 `answerSource=LLM|TEMPLATE|FALLBACK` 또는 `llmUsed=true|false`처럼 구분하는 방향이 좋다.

## 구현 전 체크리스트

챗봇 관련 코드를 수정하기 전에 아래를 확인한다.

- 이 변경이 템플릿 우회인지, LLM 프롬프트 개선인지 구분했는가?
- 특정 질문 하나만 맞추는 조건문이 아니라 같은 유형의 질문에도 적용되는가?
- stock-service 조회가 필요한 질문과 RAG 문서 답변이 필요한 질문을 섞지 않았는가?
- 빈 결과, 0개 수량, LLM 실패 시 답변이 사용자 관점에서 자연스러운가?
- 로그로 실제 흐름을 확인할 수 있는가?
- ai-service 재시작이 필요한 변경인지 사용자에게 알려야 하는가?
