# WMS AI Chatbot Workflow Guide

이 문서는 WMS AI 챗봇 작업을 할 때 반드시 먼저 읽어야 하는 설계 기준이다.
사용자가 매번 같은 의도를 다시 설명하지 않아도, 아래 기준을 기본 전제로 삼고 구현한다.

## 목표

챗봇은 단순 템플릿 응답기가 아니라 WMS 업무 흐름을 이해하고, 현재 업무 데이터와 문서 지식을 적절히 연결해 사용자에게 다음 행동을 안내하는 업무 보조자다.

답변은 빠르기만 하면 안 된다. 사용자가 "정상적으로 이해하고 답했다"고 느낄 수 있어야 한다.

## 핵심 원칙

- 단순 땜빵 금지. 조건문으로 특정 문장만 맞추는 방식보다 라우팅, 프롬프트, 데이터 근거, 답변 생성 흐름을 함께 정리한다.
- 사용자의 질문 의도를 먼저 존중한다. "어떻게 해?"는 매뉴얼 설명만 원하는 것이 아니라, 특정 상품/작업이 포함되면 현재 데이터 확인과 다음 업무 안내가 함께 필요할 수 있다.
- 템플릿은 장애 fallback 또는 아주 단순한 빈 결과 안내에만 사용한다. 정상 답변은 가능하면 LLM이 조회 결과와 대화 맥락을 보고 생성한다.
- 조회 결과가 있으면 내부 컬럼명, UUID, SQL을 노출하지 않고 업무 용어로 바꿔 말한다.
- 조회 결과가 없으면 "죄송합니다. 처리할 수 없습니다."처럼 실패처럼 보이게 말하지 않는다. 사용자 질문 기준으로 자연스럽게 없는 상태를 설명한다.
- 답변은 사용자가 바로 다음 화면에서 무엇을 해야 하는지 알 수 있게 끝나야 한다.

## 라우팅 기준

챗봇 라우팅은 크게 세 가지다.

- `WORK_QUERY`: 현재 DB 상태를 확인해야 하는 질문. 예: 재고 위치, 출고 가능 수량, 오늘/내일 처리할 작업, 내 피킹 작업, 미처리 지시서.
- `RAG`: 매뉴얼/정책/절차/상태 의미를 설명해야 하는 질문. 예: 상태값 의미, 화면 사용법, 예외 처리 기준.
- `GENERAL`: 인사, 감사, 챗봇 소개, 도움말처럼 데이터나 문서 근거가 필요 없는 대화.

특정 상품명이 포함된 출고 질문은 `WORK_QUERY`로 본다. 예: "유선 마우스 출고 어떻게 해?", "무선 마우스 출고 원해".
이 경우 단순 매뉴얼 설명보다 현재 출고 가능한 재고 위치와 수량 확인이 먼저다.
다만 답변 생성 단계에서는 `WORK_QUERY` 결과만 쓰지 않고, 출고 절차 같은 비정형 업무 지식은 RAG/vector DB 문서 근거를 함께 사용한다.

단, "출고 절차가 뭐야?", "피킹 리스트가 뭐야?"처럼 상품/현재 대상이 없는 일반 절차 질문은 `RAG`로 볼 수 있다.

## WORK_QUERY 흐름

정상 흐름은 아래 순서를 따른다.

1. LLM 또는 충분히 일반화된 라우터가 질문 의도를 판별한다.
2. 필요한 슬롯을 추출한다. 예: 상품명, 창고명, 날짜, 상태.
3. stock-service 업무 조회 API를 호출한다.
4. 조회 결과를 사용자 질문, 최근 대화 맥락, 의도와 함께 LLM 프롬프트에 넣는다.
5. LLM이 조회 결과만 근거로 자연어 답변을 작성한다.
6. LLM 실패 또는 빈 응답일 때만 fallback 문장을 사용한다.

정상 WORK_QUERY 답변에서 `llmMs=0`이고 `fallback=true`로 끝나면 의심해야 한다. 의도적으로 LLM을 생략한 템플릿 우회가 아닌지 확인한다.

## Hybrid Work Query + RAG 흐름

특정 상품의 현재 상태와 업무 절차가 함께 필요한 질문은 하이브리드로 처리한다.

질문 예시:

- "무선 마우스 출고 어떻게 해?"
- "유선 마우스 출고 원해"
- "이 상품 출고하려면 다음에 뭐 해야 해?"

정상 흐름은 아래 순서를 따른다.

1. `WORK_QUERY`로 라우팅한다.
2. stock-service에서 상품 재고 위치와 가용 수량을 조회한다.
3. 출고 절차, 승인, 피킹 리스트 생성 같은 비정형 절차는 vector DB에서 검색한다.
4. 최종 LLM 답변에는 정형 조회 결과와 RAG 문서 근거를 함께 넣는다.
5. 답변은 현재 출고 가능 여부를 먼저 말하고, 이후 절차를 문서 근거에 맞춰 안내한다.

이 흐름에서 stock-service 조회 결과는 "현재 상태의 사실"이고, RAG 문서 근거는 "업무 절차의 근거"다. 둘을 섞되 어느 하나를 추측으로 보완하지 않는다.

## 출고 방법 질문 답변 기준

질문 예시: "유선 마우스 출고 어떻게 해?", "무선 마우스 출고 원해".

좋은 답변은 현재 데이터와 업무 흐름을 함께 말한다.

예시:

```text
현재 출고 가능한 유선 마우스는 서울중앙창고의 CK-011 - 1층 위치에 있으며, 출고 가능한 수량은 34개입니다. 출고를 원하신다면 출고 지시서를 생성한 뒤 승인하고, 피킹 리스트를 생성해 주세요.
```

답변에 포함해야 할 정보:

- 상품명
- 창고명
- 위치/로케이션
- 출고 가능한 수량
- 다음 업무 단계: 출고 지시서 생성, 승인, 피킹 리스트 생성

가용 수량이 0이거나 조회 결과가 없으면 출고 지시서 생성을 권하지 않는다.

예시:

```text
현재 출고 가능한 유선 마우스 재고를 찾지 못했습니다. 출고 지시서를 생성하기 전에 재고 현황에서 가용 재고를 먼저 확인해 주세요.
```

## 날짜/작업 질문 답변 기준

질문 예시: "내일은?", "4월 30일에 뭐 있어?", "오늘 뭐 해야 돼?"

날짜 표현은 사용자가 말한 표현을 최대한 보존한다.

- 오늘: "오늘은 ..."
- 내일: "내일은 ..."
- 어제: "어제는 ..."
- 4월 30일: "4월 30일에는 ..."

빈 결과는 실패가 아니라 부재로 답한다.

예시:

```text
내일은 처리할 작업이 존재하지 않습니다.
```

할 일이 있는 경우에는 업무 유형, 문서번호, 창고, 담당자를 자연스럽게 말한다.
사용자가 "뭐 해야 돼?"처럼 행동을 물으면 마지막 문장은 가능하면 "~해야 합니다."로 끝낸다.

## 재고 위치 질문 답변 기준

질문 예시: "무선 마우스 어디 있어?", "케이블 어디야?"

좋은 답변은 위치만 말하지 않고 재고 판단에 필요한 수량도 함께 말한다.

예시:

```text
무선 마우스는 서울중앙창고의 LC-RK-ZN-SEL-ELEC-002-TECH-003-02 위치에 있으며, 현재 가용 수량은 320개입니다.
```

여러 위치가 있으면 우선 상위 몇 개를 요약하고, 필요하면 추가 조회를 유도한다.

## 답변 품질 기준

- 사용자가 화면에서 확인 가능한 업무 용어를 쓴다. 예: 출고 지시서, 승인, 피킹 리스트, 적치 지시서, 재고 현황.
- 내부 구현 용어를 노출하지 않는다. 예: intent, slots, fallback, rows, SQL, UUID.
- "처리할 수 없습니다"는 실제 오류가 아니라면 쓰지 않는다.
- 한 답변에 너무 많은 절차를 길게 나열하지 않는다. 보통 1~2문장으로 충분하다.
- 현재 화면과 다음 행동이 연결되면 좋다. 예: "재고 현황에서 확인", "출고 지시서를 생성", "피킹 리스트를 생성".

## 로그 해석 기준

정상적인 LLM 기반 WORK_QUERY는 보통 아래 로그가 함께 나타난다.

- `AI_CHAT_ROUTE`: WORK_QUERY로 라우팅
- `AI_WORK_QUERY_ROUTE`: intent와 slots 판별
- `AI_WORK_QUERY_API`: stock-service 조회 결과
- 절차가 필요한 질문이면 `AI_RAG_CONTEXT` 또는 `AI_WORK_QUERY_RAG`
- `AI_WORK_QUERY_LLM_START`
- `AI_WORK_QUERY_LLM_END`
- `AI_WORK_QUERY_END`: `llmMs`가 0보다 크고, 정상 생성이면 `fallback=false`

`fallback=true`는 실패 fallback과 템플릿 fallback을 혼동하게 만들 수 있다. 로그 개선 시에는 `answerSource=LLM|TEMPLATE|FALLBACK` 또는 `llmUsed=true|false`처럼 구분하는 방향이 좋다.

## 구현 전 체크리스트

챗봇 관련 코드를 수정하기 전에 아래를 확인한다.

- 이 변경이 템플릿 우회인지, LLM 프롬프트 개선인지 구분했는가?
- 특정 질문 하나만 맞추는 조건문이 아니라 같은 유형의 질문에도 적용되는가?
- stock-service에서 필요한 실제 데이터가 조회되는가?
- 빈 결과, 0개 수량, LLM 실패 시 답변이 사용자 관점에서 자연스러운가?
- 로그로 실제 흐름을 확인할 수 있는가?
- ai-service 재시작이 필요한 변경인지 사용자에게 알려야 하는가?
