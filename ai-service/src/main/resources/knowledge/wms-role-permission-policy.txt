[섹션: WMS 권한/역할 정책 > 기본 권한 구조]
목적: 관리자가 사용자에게 어떤 역할을 부여해야 하는지, 권한 없음 또는 메뉴 미노출 상황을 어떻게 확인해야 하는지 안내한다.

권한 모델:
- WMS는 역할(Role)과 권한(Permission)을 분리해서 관리한다.
- 사용자는 하나의 역할을 가지고, 역할은 여러 권한을 가진다.
- 권한은 리소스(Resource)와 액션(Action)의 조합으로 판단한다.
- API 권한 검사는 @CheckPermission(resource, action) 기준으로 수행된다.
- 권한 문자열은 INBOUND:READ, OUTBOUND:CREATE, INVENTORY:UPDATE 같은 형식으로 관리된다.

기본 역할:
- ADMIN: 회사 관리자 역할이다. 기본 시드 기준 전체 권한을 가진다.
- MANAGER: 매니저 역할이다. 기본 시드 기준 전체 권한을 가진다.
- OPERATOR: 현장 실행자 역할이다. 기본 시드 기준 모든 리소스 조회 권한과 MASTER를 제외한 실행/수정 권한을 가진다.
- ADMIN, MANAGER, OPERATOR는 시스템 기본 역할이며 삭제할 수 없다.
- 커스텀 역할은 관리자가 생성할 수 있지만 ADMIN, MANAGER, OPERATOR 코드는 예약어라 새로 만들 수 없다.

리소스 기준:
- INBOUND: 입고 관리
- OUTBOUND: 출고 관리
- TRANSFER: 이동 관리
- INVENTORY: 재고 관리
- STOCK_COUNT: 실사 관리
- ETC_INOUT: 기타 입출고
- MASTER: 마스터 관리
- STATISTICS: 통계

액션 기준:
- CREATE: 생성
- READ: 조회
- UPDATE: 수정 또는 실행
- DELETE: 삭제
- APPROVE: 승인

운영 안내:
- 사용자가 특정 메뉴를 보지 못하거나 "권한이 없습니다" 메시지를 보면 먼저 공통 관리 > 사용자 관리에서 사용자의 역할을 확인한다.
- 다음으로 공통 관리 > 역할/권한 관리에서 해당 역할에 필요한 리소스와 액션 권한이 포함되어 있는지 확인한다.
- 출고 지시서 생성이 안 되면 OUTBOUND:CREATE 권한을 확인한다.
- 출고 지시서 승인이 안 되면 OUTBOUND:APPROVE 권한을 확인한다.
- 입고 검수 실행이 안 되면 INBOUND:UPDATE 권한을 확인한다.
- 재고 조회가 안 되면 INVENTORY:READ 권한을 확인한다.
- 재고 조정이 안 되면 INVENTORY:UPDATE 권한을 확인한다.
- 마스터 생성, 수정, 삭제가 안 되면 MASTER:CREATE, MASTER:UPDATE, MASTER:DELETE 권한을 확인한다.
- 통계 화면이 보이지 않으면 STATISTICS:READ 권한을 확인한다.

[섹션: WMS 권한/역할 정책 > 권한 캐시와 재로그인]
목적: 역할이나 권한을 수정했는데도 사용자의 권한이 바로 반영되지 않는 상황을 안내한다.

권한 반영 흐름:
- 로그인 시 사용자의 역할에 연결된 권한 목록을 Redis에 캐싱한다.
- 캐시 키는 perm:{userId} 형식이다.
- API 실행 시 PermissionAspect가 Redis의 권한 목록과 @CheckPermission의 요구 권한을 비교한다.
- 역할 권한을 수정하면 해당 역할을 사용하는 사용자들의 권한 캐시를 무효화한다.
- 캐시가 없으면 DB에서 권한을 다시 읽어 캐싱한다.

운영 안내:
- 역할을 바꿨는데 권한이 그대로라면 사용자를 다시 로그인하게 하거나 권한 캐시가 갱신됐는지 확인한다.
- "권한 정보가 없습니다. 다시 로그인해주세요." 메시지는 Redis 권한 캐시가 없거나 비어 있을 때 발생한다.
- "권한이 없습니다: RESOURCE:ACTION" 메시지는 해당 역할에 필요한 권한 조합이 없을 때 발생한다.
- 관리자는 같은 회사의 사용자와 역할만 조회, 수정할 수 있다.
- ADMIN 역할은 일반 사용자에게 직접 부여할 수 없다.
- 관리자 계정은 비활성화할 수 없다.

[섹션: WMS 권한/역할 정책 > 게이트웨이 인증과 관리자 경로]
목적: 사용자가 관리자 화면이나 개발자 화면에 접근하지 못하는 이유를 설명한다.

게이트웨이 정책:
- API Gateway는 JWT를 검증하고 X-User-Id, X-Client-Id, X-User-Role, X-Is-Developer, X-Is-Admin 헤더를 서비스로 전달한다.
- /admin 경로는 JWT의 role 값이 ADMIN인 사용자만 접근할 수 있다.
- /developer 경로는 isDeveloper 값이 true인 사용자만 접근할 수 있다.
- /user/doLogin, /user/refresh-at 경로는 인증 없이 접근한다.
- /ai-service 경로는 현재 개발 단계에서 공개 prefix로 처리된다.

운영 안내:
- 관리자 메뉴 접근이 막히면 먼저 로그인 사용자의 role이 ADMIN인지 확인한다.
- 개발자 화면 접근이 막히면 isDeveloper 계정인지 확인한다.
- 토큰이 없거나 Bearer 형식이 아니면 인증 실패로 처리된다.
- 토큰은 통과했는데 특정 업무 API에서 막히면 Gateway가 아니라 역할 권한 매핑을 확인해야 한다.

[섹션: WMS 권한/역할 정책 > 역할 관리 시 주의사항]
목적: 관리자가 역할을 만들거나 수정할 때 업무 영향 범위를 이해하도록 안내한다.

역할 관리 기준:
- 역할은 회사별로 분리된다.
- 같은 회사의 역할만 사용자에게 부여할 수 있다.
- 같은 회사의 역할만 조회, 수정, 삭제할 수 있다.
- 시스템 기본 역할은 삭제할 수 없다.
- 사용 중인 역할은 삭제할 수 없다.
- 역할의 권한을 변경하면 해당 역할을 사용하는 사용자들의 권한 캐시가 갱신 대상이 된다.

운영 안내:
- 신규 현장 작업자에게는 OPERATOR 또는 OPERATOR 기반 커스텀 역할을 부여한다.
- 지시서 생성, 승인, 실행까지 담당하는 관리자는 MANAGER 역할을 우선 검토한다.
- 회사 사용자, 역할, 권한을 관리해야 하는 사용자는 ADMIN 역할이 필요하다.
- 일부 메뉴만 열어야 하면 커스텀 역할을 만들고 필요한 리소스와 액션만 선택한다.
- 권한을 과하게 부여하면 삭제, 승인, 마스터 수정 같은 고위험 작업까지 가능해질 수 있다.
